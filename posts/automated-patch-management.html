Automating patch management with Ansible, and the GUI I built so it would actually get used

AnsibleAutomationPatch ManagementISO 27001

Patching is the least glamorous control on the ISO 27001 checklist and the one that slips first. Not because nobody knows how to run dnf update — because doing it across 121 servers, on a schedule, with evidence, without two people starting the same run at once, is an operations problem wearing a Linux problem's clothes.

Ansible solved the Linux half years ago. This is about the other half, and the tool I ended up building because the other half is where the failures actually live.

Ansible gets you most of the way

A patch playbook is not the hard part. The shape of it is boring on purpose:

- name: Apply security updates
  hosts: "{{ target | default('patch_wave1') }}"
  serial: "{{ batch | default('20%') }}"
  become: true
  tasks:
    - name: Patch
      ansible.builtin.dnf:
        name: "*"
        security: true
        state: latest

    - name: Does this host need a reboot?
      ansible.builtin.command: needs-restarting -r
      register: needs_reboot
      failed_when: false
      changed_when: false

    - name: Reboot only if the kernel or core libraries moved
      ansible.builtin.reboot:
        reboot_timeout: 900
      when: needs_reboot.rc == 1

Two lines are doing the real work. serial is what separates "patching" from "an outage" — it turns a fleet-wide change into waves, so a bad update takes out a slice instead of a tier. And gating the reboot on needs-restarting -r rather than rebooting unconditionally is the difference between a maintenance window you finish and one you don't.

What the playbook does not give you is the thing an auditor asks for six months later: who ran it, when, against which hosts, with what output, and can you show me the last two quarters of that.

Why a GUI, when the CLI works fine

I'm perfectly happy driving Ansible from a terminal. That was never the constraint. Three other things were:

  • Evidence. "We patch monthly" is not an audit answer. A list of job records with timestamps, host lists, full captured output and a diff against last month's report is an audit answer.
  • Handover. At 2am, whoever is on call should not have to remember the right combination of --limit, --tags and extra-vars.
  • Scheduling with a memory. cron will cheerfully start a second patch run while the first one is still going, and never mention it.

So I built Ops Workflow: a FastAPI app behind an nginx TLS terminator, one Docker Compose stack, mounting the Ansible tree and the SSH keys, with SQLite for job history. It's a private tool I write and maintain myself, sized for one estate rather than for distribution — the design decisions below are the ones that mattered for running it against 121 servers, not a general framework. 

browser ──► nginx (443 TLS) ──► app (FastAPI + scheduler)

app mounts:
  ├── /etc/ansible   playbooks, inventory, cfg
  ├── /root/.ssh     keys, read-only
  └── ./data         SQLite: jobs, schedules, MFA

Nothing exotic. The interesting part isn't the stack, it's which guard rails turned out to matter.

The guard rails are the product

Dry run is on the way to the real run, not beside it

The run panel is ordered the way the work should be ordered: lint, syntax check, --check --diff, then the real run behind a type-to-confirm modal. Putting the destructive action last and behind an extra deliberate step costs about four seconds and removes an entire category of mistake.

The same playbook cannot start twice

This is the guard I care about most, because it's the failure I could actually see coming. A schedule fires at 02:00. Someone clicks Run at 02:01 because they didn't know the schedule existed. Now there are two ansible-playbook processes against the same hosts, fighting over the same package manager lock.

The second attempt is refused — already running as job 412 — rather than allowed to race. Schedules carry the same rule as skip-if-running, so a slow wave that overruns its window doesn't get lapped by the next one.

Concurrency bugs in ops tooling don't announce themselves. They show up as a corrupted RPM database on one host, weeks later, and nobody connects it back to two runs that overlapped by ninety seconds. Refuse the second run.

Failed hosts rerun without rerunning everything

Ansible already writes a .retry file listing the hosts that failed. Surfacing that as a rerun failed hosts button means the response to "three of forty hosts timed out" is one click against three hosts, not a second full wave against forty.

Evidence is a feature, not a byproduct

Every run is a job record: status, host list, full log, replayable. Reports render as text, CSV-as-table, sandboxed HTML or JSON, and — the part that turned out to matter most — any two reports can be compared as a unified diff.

That diff view is what makes a compliance conversation short. Last month's report against this month's, showing exactly which hosts moved and which didn't. The ones that didn't move are the interesting ones, and before this they were invisible unless you went looking.

Logs grow without limit if you let them, so retention is automatic: GUI_AUTOCLEANUP_DAYS defaults to 90 and sweeps finished jobs, their log files and old reports once a day. It never touches a running job.

Notify on start, not only on finish

Scheduled jobs push a Telegram message when they start and when they finish, and there's a generic webhook (JSON or Slack-shaped) for teams that live somewhere else.

The start notification is the one people leave out, and it's the one that catches the worst failure mode: a scheduled job that silently never fired. A finish-only notification is indistinguishable from a scheduler that quietly died — in both cases your phone stays quiet. Announcing the start turns absence into a signal.

Login attempts alert the same way — success, failure, and bad MFA code, with IP, timestamp and user-agent.

The tradeoffs I took on purpose

This is where a reviewer would push, so I'd rather push first. Every one of these is written into the README, because a tool whose limits are undocumented gets trusted further than it deserves:

  • Playbooks run as root inside the container. That's the same privilege they had when I ran them from a root shell, which is what this replaced — but it is not a sandbox, and it shouldn't be mistaken for one. It lives behind the firewall.
  • It is single-admin by design. One username, one password. Fine for me; not fine for a team that needs per-person accountability. That case wants SSO in front of it, not a second row in the settings table.
  • The API token bypasses MFA. A static bearer token for CI gets the same access as a logged-in session with no second factor. It is a root password with a friendlier name, and it should be rotated like one.
  • MFA recovery ends in a container exec. Eight one-time recovery codes at enrolment, and if those are gone too you clear the MFA state out of SQLite by hand. Blunt, documented, and preferable to a self-service reset path that becomes the weakest link in the auth story.

Writing these down was not a formality. Half of them changed shape once I had to justify them in a paragraph.

Where it landed

The number that matters isn't in the tool, it's in what changed after it: patch compliance now consistently meets our KPI target, and vulnerability counts coming out of the vulnerability management scans have dropped as a direct result — patching stopped being the thing that fell behind between audits and became something that just runs. That's the outcome the report diff and the concurrency guard were built to protect; the software was never really the point.

What I'd do next

  • Per-person identity via an SSO-aware reverse proxy, so the audit trail says who rather than admin.
  • Drop the run privilege from root to a scoped account with a narrow sudoers policy on the targets.
  • Wire the report diff into the CAB pack so change review gets last month's delta without anyone assembling it by hand.

The automation was never the interesting part. Ansible has been able to patch a fleet for a decade. What took the work was making the thing safe to run at 2am, and making it produce, without anyone having to remember to, the evidence that it ran at all.
